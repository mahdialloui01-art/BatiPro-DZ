# BatiPro DZ

برنامج تسيير محل مواد البناء، بواجهة Flutter عربية RTL. التطوير الحالي موجّه إلى **Windows + PostgreSQL**، وتطوير Android مؤجّل.

## البنية الحالية

- **Windows:** تطبيق Flutter Desktop، تخزين محلي SQLite عبر `AppStorage` للعمل المحلي.
- **API:** FastAPI / Python 3.12.
- **Database:** PostgreSQL 16.
- **Authentication:** كلمات مرور PBKDF2-HMAC-SHA256، ورموز وصول HMAC موقّعة صالحة 12 ساعة.
- **Windows secure storage:** عنوان الخادم ورمز الدخول محفوظان عبر مخزن بيانات الاعتماد الآمن في Windows.
- **Transactions:** فواتير الشراء والبيع وحركات المخزون تُسجّل ضمن معاملات PostgreSQL ذرّية.

## تشغيل خادم PostgreSQL محلياً أو على Windows Server / Linux Server

1. انسخ `.env.example` إلى `.env`.
2. غيّر كلمة مرور PostgreSQL ومفتاح توقيع الرموز ومفتاح تأسيس أول حساب إلى قيم عشوائية قوية. لا ترفع ملف `.env` إلى Git ولا تشارك هذه المفاتيح.
3. شغّل Docker Compose. حاوية API تطبّق جميع ملفات SQL بالترتيب قبل تشغيل الخدمة، وتوقف التشغيل إذا فشل أي ترحيل:

```bash
docker compose up -d --build
```

4. افحص صحة الخدمة:
   - `http://localhost:8000/health/live`
   - `http://localhost:8000/health/ready`
5. افتح `http://localhost:8000/docs` على جهاز الخادم، واستعمل `POST /auth/register` لإنشاء المؤسسة والحساب الأول. يجب إرسال قيمة `BATIPRO_BOOTSTRAP_SECRET` الموجودة في ملف الخادم السري. هذا المفتاح للتأسيس الأول فقط، ولا يُدخل في تطبيق Windows.
6. في BatiPro DZ على Windows افتح **الإعدادات ← الاتصال بخادم PostgreSQL**، أدخل عنوان API ثم البريد وكلمة المرور اللذين أنشأتهما.

### نسخ قاعدة PostgreSQL احتياطياً واسترجاعها

تعمل خدمة `db-backup` على أخذ dump يومي تلقائياً والاحتفاظ بآخر 7 أيام داخل volume مستقل. هذا يحمي من بعض أخطاء قاعدة البيانات لكنه ليس نسخة خارجية؛ انسخ مجلد النسخ إلى تخزين منفصل خارج الخادم بانتظام. لإنشاء dump من مجلد المشروع:

```bash
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > batipro-postgres.dump
```

لاسترجاع النسخة إلى قاعدة فارغة أو بعد إيقاف API:

```bash
cat batipro-postgres.dump | docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists'
```

اختبر الاسترجاع دورياً على قاعدة منفصلة قبل اعتباره خطة تعافٍ صالحة. يمكن استخراج أحدث dump من volume النسخ عبر `docker compose run --rm --entrypoint ls db-backup -lh /backups`، وانسخ الملف خارج الخادم قبل أي صيانة كبيرة.

> **تنبيه أمني:** لا تعرّض منفذ API العام عبر HTTP غير المشفّر. عند الاتصال عبر الإنترنت استعمل HTTPS خلف reverse proxy مع شهادة TLS وجدار ناري ونسخ احتياطي دوري لقاعدة البيانات. ملف Compose يفتح المنفذ 8000 للشبكة المضيفة فقط؛ إعداد TLS والنشر العام مسؤولية بيئة الاستضافة.

## حسابات البائعين المتعددة

- يستطيع حساب المسؤول المتصل بالخادم فتح **الإعدادات ← إدارة حسابات البيع وإضافة بائعين**.
- لكل بائع اسم مستخدم مستقل وكلمة مرور لا تقل عن 8 أحرف؛ تُخزّن كلمة المرور على الخادم كـ PBKDF2-HMAC-SHA256 ولا تُعرض بعد الإنشاء.
- يسجّل البائع الدخول إلى API باسم المستخدم أو البريد وكلمة المرور. دور `cashier` يسمح بتسجيل فواتير البيع فقط؛ لا يسمح بإنشاء المنتجات أو المشتريات أو تعديل المخزون أو إدارة الحسابات.
- يستطيع المسؤول تعطيل حساب بائع مع الاحتفاظ بالفواتير القديمة. فواتير البيع الجديدة تحفظ معرّف الحساب الذي أنشأها.
- أضيف ترحيل قاعدة البيانات `003_seller_usernames.sql` لأسماء المستخدمين و`004_sales_invoice_seller.sql` لربط الفاتورة بالبائع. تُطبّق تلقائياً عند تشغيل خدمة API.

> إدارة الحسابات موجودة على الخادم المشترك، لكن واجهة دخول POS الحالية ما زالت تعتمد بوابة PIN المحلية. لا تعتبر حسابات البائع البعيدة مرتبطة بالكامل بواجهة POS على كل جهاز حتى يكتمل ربط تسجيل دخول البائع ومبيعات شاشة POS مباشرة بـ API؛ لا تستخدمها بعد كتشغيل إنتاجي متعدد الأجهزة.

## واجهات API المنفذة

- `GET /health/live` و`GET /health/ready`
- `POST /auth/register` و`POST /auth/login` و`GET /me`
- `GET /warehouses`
- `GET /products` و`POST /products`
- `GET /stock` و`POST /stock/adjustments`
- `GET/POST /suppliers` و`GET/POST /customers`
- `POST /purchases` و`POST /sales`

تتحقق الخدمة من عضوية المستخدم في المؤسسة في كل طلب، وتمنع الحسابات ذات دور `viewer` من الكتابة. حركات المخزون تستخدم مفاتيح idempotency لمنع تكرار التسجيل. فواتير البيع تتحقق من الرصيد المتاح قبل الخصم. شراء حديد التسليح بالوزن يحوّل الوزن إلى عدد القضبان من وزن القطعة المسجل على المنتج.

## حالة الربط بين تطبيق Windows والخادم

تمت إضافة عميل API إلى Flutter وواجهة إعداد عنوان الخادم وتسجيل الدخول. أضيفت أيضاً عملية **استيراد أولي لمرة واحدة** من SQLite إلى PostgreSQL: المنتجات والمخزون الحالي والموردون والزبائن وفواتير الشراء والبيع التاريخية. يُسجّل المخزون الحالي كرصد افتتاحي، وتُحفظ الفواتير التاريخية دون إعادة حركات مخزونها حتى لا تتضاعف الكميات. العملية محمية بمفتاح idempotency وبصمة الحمولة، وتبقى بيانات SQLite كما هي على الجهاز. أُضيفت الآن مزامنة مستمرة يدوية بين أجهزة Windows عبر `POST /sync/push` و`GET /sync/pull`: التعديلات المحلية تُكتشف عند الضغط على «مزامنة التغييرات»، وتُرسل بمراجعات لكل مفتاح، ثم تُستقبل تغييرات بقية الأجهزة عبر سجل أحداث مرتب. إذا عدّل جهازان نفس البيانات على أساس إصدار قديم، يرفض الخادم الكتابة المتعارضة ولا يكتب فوقها بصمت. معرّف كل تثبيت محفوظ في مخزن Windows الآمن. هذه مزامنة يدوية وليست مزامنة خلفية تلقائية؛ يلزم اختبار سيناريوهات الاستخدام الحقيقية قبل اعتمادها تجارياً، كما أن معالجة التعارضات تحتاج قراراً من المستخدم ولا تُحل تلقائياً.

لا توجد قاعدة PostgreSQL مستضافة أو بيانات دخول جاهزة ضمن المستودع؛ يجب نشر الخادم وضبط أسراره أولاً.

## التطوير والاختبارات

### Windows

```powershell
flutter pub get
flutter analyze --no-fatal-infos
flutter test
flutter build windows --release
```

### Backend / PostgreSQL

```bash
pip install -r backend/requirements.txt
python backend/scripts/migrate.py
cd backend
PYTHONPATH=. pytest -q
```

GitHub Actions يشغّل بناء Windows واختبار تشغيل EXE، ويختبر Backend على PostgreSQL 16.

## بيانات مهمة

- ملفات SQLite المحلية تبقى على جهاز Windows حتى يتم تنفيذ مزامنة موثوقة.
- لا تحذف بيانات SharedPreferences القديمة يدوياً؛ عملية الترحيل القديمة تنقل مفاتيح `batipro_` إلى SQLite وتحتفظ بالأصل.
- لا توجد حالياً مزامنة Offline/Online مكتملة، ولا استعادة تلقائية من النسخ الاحتياطي.
